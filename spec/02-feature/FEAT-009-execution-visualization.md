# FEAT-009：可重建执行可视化

- 状态：进行中
- 负责人：Codex
- 创建日期：2026-08-12
- 最后更新：2026-09-04
- 所属产品：[PROD-001](../01-product/PROD-001-local-spec-loop.md)
- 所属阶段：Phase 4 可观测性前置能力；不依赖或启动自动 Controller

## 用户价值

作为正在推进一个工程的用户，我希望随时打开该工程的执行图，立即知道当前正在处理哪个 Task、处于哪个步骤、这个步骤在做什么，以及历史 Task 和步骤分别花了多久，从而无需阅读聊天记录或逐个检查 `.spec-loop/` 文件就能掌握进展。

## 行为说明

用户在任意已初始化 Project 上运行 `spec-loop view <project-dir>`，得到仅监听本机回环地址的只读 Web 页面。页面从项目路线图、波次看板和 Feature/Task 规格重建 H1～H15 主链，所有 H 节点使用统一尺寸。点击某个 H 后只在该节点下原位展开子 Task DAG：依赖从左到右推进，同列节点表示可并行；再次点击收起，点击另一 H 切换展开。点击 Task 继续在当前 H 内展开 Round、步骤和耗时明细，不切换页面。

当用户从交互终端启动 Task、批次或 Harness 时，Spec-Loop 应直接复用或启动该 Project 的后台只读视图，打印可点击 URL 并默认打开浏览器；用户不需要另开终端、记忆 `view` 命令或手工寻找端口。非交互/CI 环境只打印 URL，不自动启动图形界面；`--no-view` 可以显式关闭该行为。

页面和可选快照都是投影：删除后可从项目 `.spec-loop/` 的 Task State、Ledger、Evidence、Harness 产物和新增的执行事件流完整重建，不成为新的 Task、Harness 或 Delivery 状态源。

旧项目可以立即展示已有事实。现有 Gate 的 `duration_ms` 可作为精确耗时；只能从相邻时间点推导的耗时必须标记为“推算”；缺少时间事实的历史阶段显示“未知”，不得使用文件修改时间或臆测值伪装成精确耗时。升级后产生的执行步骤通过追加式事件获得完整起止时间。

## 业务规则

1. 当前 Task 继续由 `TASK_STATE.md` 和既有 Project 派生规则决定；可视化不得维护另一份可编辑状态。
2. 当前步骤由未闭合的执行步骤事件派生；无活动步骤时显示当前生命周期状态和下一动作，不猜测 Agent 正在工作。
3. “耗时”必须区分墙钟跨度、主动执行时间、等待用户时间和未记录时间；默认不把等待时间计入主动执行时间。
4. 每个步骤至少展示名称、目的说明、状态、开始时间、结束时间或已运行时间、结果，以及可用的 Evidence/Artifact 引用。
5. 新增执行事件是只描述发生事实的追加式审计流；它不能覆盖 `TASK_STATE.md`、`LOOP_LEDGER.jsonl`、Harness State 或 Evidence 的权威字段。
6. 事件必须具有项目内单调序号、稳定 step run ID、时间、Task/Round、前序哈希和自身哈希；开始事件与终止事件使用同一个 step run ID 配对。
7. 进程崩溃后未闭合步骤显示为“中断/待协调”；只有 reconcile 产生明确事件后才能显示为成功或失败。
8. 页面只读、默认只监听 `127.0.0.1`，不提供 Task 状态修改、命令执行、Connector 写入、文件编辑或任意路径读取。
9. 页面不得显示 Prompt 正文、Secret、完整环境变量或未脱敏 stdout/stderr；步骤说明使用受控类型文案和显式安全摘要。
10. 投影解析遇到损坏、哈希断链、非法路径或相互矛盾的权威事实时必须显示明确错误并 fail closed，不得静默跳过后给出“正常”结论。
11. 同一 Project 默认只保留一个可复用的后台 view 进程；CLI 提供 `view start/status/open/stop`，启动类命令输出同一稳定入口，不因重复执行产生多个无人管理的端口和进程。
12. view 启动或浏览器打开失败不得阻断 Task/Harness；CLI 必须保留任务结果并给出可复制 URL、明确诊断和手工恢复命令。

## 验收标准

- AC-1：打开 Project 页面后，首屏明确显示当前 Task、Round、生命周期、当前步骤、步骤目的、已运行时间和下一预期动作。
- AC-2：历史 Task 时间线同时展示墙钟跨度、主动执行、等待和未记录时间；步骤明细展示起止、耗时、结果和 Evidence 引用。
- AC-3：删除可视化缓存或快照后，系统能只从 `.spec-loop/` 权威事实和执行事件重新生成同语义的执行图。
- AC-4：旧项目无需迁移即可打开；精确、推算和未知耗时在数据与界面上可区分，缺失事实不被伪造。
- AC-5：运行中的步骤会随时间推进，新增事件在不刷新整页的情况下可见；时钟推进只更新数字、进度与活动节点，不造成页面结构闪烁；进程异常后未闭合步骤显示为中断或待协调。
- AC-6：事件流被截断、重排、篡改，或 Artifact/Task 路径越出 Project 时，重建与页面明确报错且不展示误导性完成状态。
- AC-7：服务仅绑定本机回环地址且只暴露只读查询；页面与接口不泄漏 Prompt、Secret、环境变量或未脱敏执行输出。
- AC-8：在 200 个 Task、每个 200 个事件的基准 Project 上，冷重建不超过 2 秒，追加一个事件后的增量刷新不超过 500 毫秒。
- AC-9：桌面和窄屏下都能完成“找到当前步骤、比较历史耗时、展开失败步骤、定位 Evidence”四条真实浏览器路径，并通过人工视觉 Review。
- AC-10：默认完整展示尺寸一致的 H1～H15 主链；每次最多展开一个 H 的完整子 Task DAG，Task 详情原位展开，不进入 H 二级页面。
- AC-11：H 状态由子 Task 实际状态优先派生；路线图与子 Task 冲突时不得显示绿色完成，默认定位到最新未完成 H，并在总览顶部说明整体进度和当前位置。
- AC-12：Task 详情按“结论、耗时构成、Task→Round→活动时间线、数据来源”分层展示；并行活动按区间互斥归类，构成比例不得重复计算。
- AC-13：Task 节点固定尺寸并支持两行标题和完整悬停文本；完成态使用中性底色，进行中、失败与等待保留高显著状态色。
- AC-14：支持进行中、失败/等待、耗时异常、已交付筛选及总耗时排序；DAG 筛选只淡化节点，不删除依赖节点或改变拓扑。
- AC-15：交互终端启动 Task/批次/Harness 时，5 秒内输出并默认打开当前 Project 的可视化入口；重复启动复用同一服务，`status/open/stop` 可管理生命周期，CI 与 `--no-view` 不触发浏览器。
- AC-16：下拉、按钮、分段筛选、标签、提示、面包屑、空状态与告警使用本地打包的 Ant Design 组件；DAG 和 H/Task 数据节点保留专用可视化，不依赖公网资源。
- AC-16：存在未闭合执行步骤时，顶部当前工作优先指向最近开始且仍在运行的步骤所属 Task；多个 Task 同时运行时显式列出并发活动，不得仅按 Task State 更新时间选择错误 Task。

## 非功能要求

- 性能：常用规模冷重建不超过 2 秒；前台使用条件 GET 或增量读取，空闲时不持续高 CPU。
- 安全与隐私：只读、loopback-only、路径边界检查、中央脱敏；不渲染原始 Agent 输出。
- 兼容性：Node.js 22+；旧 schema 保持可读，新事件能力采用显式 schema version。
- 可观测性：投影暴露来源、精度、缺失和解析错误；页面自身不写业务事实。
