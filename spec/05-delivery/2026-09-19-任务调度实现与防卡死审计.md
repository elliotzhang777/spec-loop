## 一句话结论

spec-loop 的调度不是一个“定时器直接启动 Agent”的薄层，而是由报告扫描、Ready 规划、Project/Task Lease、资源声明、受预算约束的 Worker、独立 Supervisor、watchdog 和恢复对账组成的本地控制面。

当前主链路已经具备超时、无进展熔断、PID 身份校验、fencing token、波次心跳和崩溃恢复。本次进一步统一了控制面锁、合并心跳写入、Supervisor 失联恢复、Lease 续租、RetryWait/DeadLetter、层级资源冲突和调度 SLO，重点消除“进程仍在但系统不再前进”的软卡死。

## 调度主链路

```text
scheduler report（只读扫描）
        ↓
run-ready 生成 Ready / Held 计划
        ↓ --execute
确认独立 Supervisor 健康
        ↓
对账中断波次 reconcileInterruptedWaves
        ↓
获取 Project Lease（一个 Project 同时一个有效调度波次）
        ↓
按 max_parallel 启动 Worker 池
        ↓
每个任务获取 Task Lease + resource claim + fencing token
        ↓
预留本任务 Token / Cost 额度
        ↓
prepareRoleInvocation → runRoleInvocation → ingestSucceededRoleResult
        ↓
结算 usage、释放 Task Lease
        ↓
释放 Project Lease，持久化波次终态
```

这里有两个重要原则：

1. “准备执行”和“接受结果”都必须受 Lease 约束。旧 Worker 即使晚返回，也会因 fencing token 过期而被拒绝。
2. Provider 退出成功不等于工作流成功。结果还必须经过 Evidence 摄入；没有合法 `RESULT.json` 时会停在 `awaiting_ingestion`，不会制造虚假 PASS。

## 两类调度器

### Report-only Scheduler

`src/report-scheduler.ts` 只读取 Project、Task 和执行投影，生成稳定的建议、去重键、Ready/blocked 原因、风险和成本估算。它不创建 Task，也不执行 Agent。

它通过 `.spec-loop/scheduler-report.lock` 防止并发扫描。本次锁文件增加 `pid + process_started_at`：

- PID 仍存在且启动身份一致：认为真实扫描仍在运行，拒绝并发进入；
- PID 已死亡或 PID 已被复用：回收锁后重新扫描；
- owner 缺失：先保留 30 秒保护窗口，避免把“刚建目录、尚未写 owner”的活锁误删；
- 释放时再次核对 owner 身份，只删除自己持有的锁。

### 执行 Scheduler

`src/scheduler-control.ts` 负责真实波次。`planReadyWave` 读取验收状态，把 `m_working / plan_compiled / v_passed` 分别映射为 M、V、R；已有非终态 invocation 的任务进入 Held，不重复派发。

`runReadyWave` 的关键顺序是：

1. 启动或复用健康的独立 Supervisor；
2. 对账 Driver 已死亡或心跳陈旧的旧波次；
3. 读取 Ready 计划并处理 Candidate baseline drift；
4. 获取 Project Lease；
5. 并发 Worker 获取 Task Lease；
6. 从同一个波次剩余额度中预留 Token/Cost，避免每个 Worker 都看到完整预算；
7. 运行角色并实时累计 usage；
8. 达到 elapsed、Token、Cost 或 usage 不可证明时触发 fuse；
9. 停止活动任务、释放 Lease、写入波次终态。

## 为什么不会把“活着”误判为“有进展”

每个角色和 Effect 都区分两类时间：

- `heartbeat_at`：Controller 还活着；
- `last_progress_at`：Provider 最近一次产生 stdout、stderr 或 usage 变化。

因此，一个进程即使每两秒正常写心跳，只要长期没有真实输出或 usage 进展，仍会被判定为 `no_progress`。默认 Provider 无进展阈值为 300 秒，随后执行 TERM→KILL。

这是防卡死的核心：心跳解决“进程死了没人知道”，进展时间解决“进程没死但永远不结束”。

## Supervisor 与 watchdog

Supervisor 是独立于波次 Driver 的常驻进程。波次 Driver 崩溃后，它仍能扫描：

- running invocation 的 PID 是否还匹配原启动身份；
- Effect 心跳是否陈旧、是否长期无进展；
- workflow Driver lock 的 owner 是否死亡或 PID 复用；
- 波次心跳是否陈旧、是否超过 elapsed deadline。

每轮 watchdog 在独立子进程中运行，带周期硬超时和 stdout/stderr 上限。本次修复前，超时路径只发送 `SIGKILL` 就立即把 Worker 标记清空，理论上可能在旧进程尚未真正退出时开始下一轮。

修复后的语义是：

```text
周期超时 / 输出越界
        ↓
读取 watchdog PID 启动身份
        ↓
TERM，等待宽限期
        ↓
仍存活则 KILL
        ↓
再次验证 PID 已消失或身份不再匹配
        ↓
清空 worker_pid，Supervisor 进入 degraded
        ↓
下一周期才允许重新运行 watchdog
```

若停止无法验证，错误会明确记录为 `watchdog worker stop was not verified`，而不是把“已经发信号”冒充成“已经停止”。

## Lease、资源与 fencing

Project Lease 保证一个 Project 同时只有一个有效调度波次。Task Lease 进一步约束单个 Task 和资源：

- 同一 Task 不能有两个有效 Lease；
- `repo:` 与其 `branch:`、父子 `module:` 会产生层级冲突；资源可声明 `#read`、`#write`，工具还可声明 `#units/capacity`；
- 每次 Lease 获取单调递增的 fencing token；
- Worker/Driver 使用原 fencing token 与 owner nonce 续租，且续租后的到期时间不能超过波次绝对截止时间；
- 结果摄入前重新验证 Task Lease、Project Lease、token 和角色 invocation；
- Lease 过期、Kill、token 陈旧或角色不匹配都会拒绝结果。

锁解决的是“同一时刻谁能修改控制文件”，Lease 解决的是“跨一段执行时间谁仍有资格提交结果”。二者不能互相替代。

## Pause、Kill 与 reconcile

- Pause：与 Lease 获取共用 Scheduler mutex。Pause 返回后，新 Lease 不能再从并发窗口穿透；已运行工作允许按既定停止策略处理。
- Kill：先在同一互斥边界内写入 `paused=true / killed=true / reconcile_required=true`，再取消 invocation、Effect、Driver 和活动 Lease。
- reconcile：确认没有仍在运行的角色后，才在互斥边界内清除 `killed` 和 `reconcile_required`。
- Resume：若尚未 reconcile，直接拒绝。

这个状态顺序的目的，是让“停止新派发”先成为持久事实，再处理较慢的进程停止和现场保存。

## 本次发现并修复的问题

| 问题 | 原影响 | 修复 |
|---|---|---|
| report-only 扫描进程崩溃后留下锁 | 后续扫描永久提示 already running | 锁绑定 PID 启动身份并自动回收死亡 owner |
| Scheduler mutex 在建目录与写 owner 之间崩溃 | 留下无 owner 目录，控制命令持续 busy | 增加 owner 缺失保护窗口和死亡锁回收；获取失败时清理自己创建的目录 |
| Pause/Resume 与 Lease 获取不在同一互斥边界 | 极小概率 Pause 返回前后仍穿透一个新 Lease | 控制状态切换和 Lease 共用 mutex |
| watchdog 超时后未等待旧 Worker 真正退出 | 极端情况下 watchdog 重叠、晚写状态 | TERM→KILL 后校验 PID 启动身份已经消失，再清空 Worker 标记 |
| 事务、事件、Scheduler、Connector 各自实现锁 | PID 复用、无 owner 目录和释放误删语义不一致 | 统一 `OwnedDirectoryLock`，记录 PID 启动身份、nonce、创建时间，隔离回收并校验释放所有权 |
| 波次与 Supervisor heartbeat Promise 链式排队 | 慢磁盘时待写任务无界增长 | 使用 latest-value writer，同一时刻一个写操作且只保留最新快照，终态强制 flush |
| Supervisor 活着但心跳过期 | `run-ready` 只能拒绝，需人工 stop/start | 校验 PID 身份后自动 TERM→KILL 并重启；首次 watchdog 成功前不得派发 |
| watchdog 确定性连续失败 | 周期性无限重试 | 连续失败达到阈值后打开 circuit，保持 degraded 诊断状态 |
| 长任务 Lease 只能依赖初始 TTL | 无法区分健康长任务与死亡 Worker | Project/Task Lease 定期续租，失败立即熔断且不能突破波次截止时间 |
| 基础设施失败重新进入 Ready | 相同错误反复消耗 Provider/Token | 基础设施错误进入有界 RetryWait；相同指纹再次出现或确定性工具错误进入 DeadLetter |
| 资源只做字符串相等比较 | 父子模块、仓库/分支和容量资源可并发冲突 | 增加层级、读写模式和工具容量冲突模型 |
| 临时 Supervisor 被测试强杀后残留 | 后续测试和本地状态出现假卡死 | 增加 `--test-mode`、session ID 与 `--max-runtime-seconds` 自退出边界 |
| 跨根事务 recover/prepare/commit 无统一互斥 | 并发创建目录报 `EEXIST`，恢复者可能重复处理 journal | 全流程纳入 `.spec-loop-cross-tx-lock`；新增 100 并发事务回归 |
| 半写 `owner.json` 被立即当作坏锁回收 | 正在创建的锁可能被抢走 | `invalid_owner` 同样遵守保护期；recovery mutex 下复核 inode 与 owner 摘要后才隔离回收 |
| 根进程已退出但逃逸孙进程仍持有管道 | Provider/Gate Promise 永远等不到 `close` | Managed Process 分离执行和 pipe drain 期限，主动销毁本地 stream 并记录 `termination_verified`、`pipe_drain_timed_out` |
| Supervisor 熔断仅存在内存 | `run-ready` 重启 degraded 实例后清空 circuit | circuit 持久化、显式 reset、`ok:false` 计失败、十分钟自动重启上限三次 |
| watchdog 串行停止任务 | 一个慢停止饿死后续任务和整轮 watchdog | 先批量写 stop intent，再四路有界停止；超时保留 `stop_incomplete` 供下轮对账 |
| recovery mutex 固定等待十秒 | `maxWaitMs: 0` 的控制锁仍可能卡十秒 | 传递外层绝对 deadline；零等待只做非阻塞尝试并返回正常 busy |
| Wave Driver 启动身份可为空 | 后续存活检查退化为只比较 PID | 在任何 Supervisor/波次副作用前强制取得启动身份 |
| `launchctl` 与手工工作命令无超时 | 非主路径命令仍可能无限等待 | 统一使用 Managed Process；分别设置 10 秒和默认 300 秒硬期限 |

## 排障顺序

当界面或命令看起来不再前进时，建议按以下顺序判断：

```bash
spec-loop scheduler control supervisor-status <project-dir> --json
spec-loop scheduler control health <project-dir> --json
spec-loop scheduler control status <project-dir> --json
spec-loop scheduler control reconcile-waves <project-dir> --json
```

重点看：

1. Supervisor 是否 `running=true, healthy=true`；
2. invocation 是 `controller_stalled` 还是 `no_progress`；
3. wave 是 `dead_driver`、`stalled` 还是 `overdue`；
4. CONTROL 是否处于 `killed/reconcile_required`；
5. Task/Project Lease 是否已过期但仍被误认为活动；
6. `SUPERVISOR.json.last_error` 是否包含无法确认停止、事务锁 busy 或文件系统错误。

只读检查后，再按事实选择：

- 死亡/陈旧执行：`watchdog --apply`；
- Driver 崩溃：`reconcile-waves --apply`；
- Kill 后恢复：先 `reconcile`，再 `resume`；
- 不确定时先 `pause`，不要直接删除 `.spec-loop` 下的锁、Lease 或 Evidence。

## 当前保留边界

- 文件系统 Promise 超时不能取消已经进入内核的写操作。本实现采用 fail-closed：停止新派发、终止对应控制进程并由 PID 身份恢复，而不声称底层 I/O 已被取消。
- 调度公平性使用 Task 状态年龄、下游阻塞数量和重试惩罚计算稳定分数；关键路径和 Heavy 人工确认规则仍由 Acceptance Schedule 决定，评分不能绕过确认。
- SLO 以有界汇总和每个波次的任务指标保存，不保留无界高基数时间序列。外部长期趋势分析仍应由单独的导出器承担。
- 生产 Supervisor 不绑定调用 CLI 的父进程；只有显式 test mode 才有最大生存期。
- 2026-09-06 遗留 `_view-serve` PID 28774 经用户单独授权后已通过 Execution View 控制命令安全停止；进程、监听端口和 marker 均已确认消失，临时目录未删除。异常中断自清理仍由 lifecycle 回归持续覆盖。
