## 1. 规范强度与例外

- **必须/禁止**：不可绕过；无法满足时必须在 `WEB-TASK` 中记录原因、影响和恢复计划。
- **应该**：默认遵守；例外需在工单或评审记录中说明。
- **可以**：按场景选择，不作为验收门禁。
- 引入新框架、状态方案、设计系统或构建链迁移属于架构变化，必须单独立项并同步后端主规格库的 ADR/Design。
- 本文件不列项目特定页面、字段和接口，避免形成第二事实源。

### 2.1 格式化基线

- 使用 2 空格缩进、单引号、分号和尾随逗号，单行建议不超过 120 字符。
- 格式规则由 Prettier/ESLint 等工具统一执行，不在评审中反复争论手工格式。
- 不得为无关需求批量格式化文件或调整 import 顺序，避免制造评审噪音。

## 3. 事实源与后端契约

按以下优先级理解需求：

1. 后端主规格库中的 Product、Feature 和验收标准；
2. 后端 [`04-design/`](../../../backend/spec/04-design/) 中的 API、事件和数据契约；
3. 当前 `WEB-TASK` 的页面范围和端内决策；
4. 本开发规范；
5. 现有代码模式。

- 前端不得根据视觉稿或现有返回样例臆造业务规则、接口或字段。
- 请求/响应、错误码、枚举、可空性和 SSE 事件必须与后端正式契约一致。
- 对接逻辑变更前先检查后端 Design；契约变化时，后端 Task 与对应 `WEB-TASK` 同步修改和验证。
- 前端类型可以表达页面模型，但必须在数据边界集中完成契约模型到页面模型的转换。
- 发现契约冲突时暂停扩散实现，在工单记录问题并修正更高层事实源。

## 4. 目录与模块边界

默认项目结构：

```text
src/
├── assets/        # 静态资源
├── components/    # 跨页面复用的基础/业务组件
├── constants/     # 跨模块稳定常量
├── hooks/         # 可复用 Hooks
├── layouts/       # 全局布局
├── pages/         # 页面与路由编排
├── services/      # API、SSE 和契约转换
├── styles/        # 全局样式、变量和主题
├── types/         # 跨模块类型
└── utils/         # 无业务或边界明确的工具
```

- 页面组件负责编排路由、数据和业务组件；通用 UI 下沉到 `components/`，全局布局放 `layouts/`。
- 共享代码只有在语义稳定并被多个场景复用后才上提，不建立万能组件或万能工具目录。
- 模块对外暴露最小 API，避免跨目录引用内部实现。
- 请求、协议解析、类型转换和错误归一化集中在 `services/` 或等价边界，页面不得散写。
- 删除废弃代码、无效样式和调试输出，不保留注释掉的大段代码或“以后可能用”的平行实现。

## 5. 请求、类型与数据

- 所有 HTTP 请求通过统一 request 层，集中处理基础地址、超时、取消、认证、`ApiResult<T>`、错误码和用户提示。
- 页面不重复解析响应包络，不直接拼接 URL、认证 Header 或裸请求对象。
- 复杂入参用明确的 builder/mapper 函数组装，并对可选、默认和非法值做显式处理。
- 外部数据先按不可信数据处理；使用明确类型，未知数据从 `unknown` 校验和收窄，禁止无说明的 `any`。
- 金额、日期、时区、数字、单位和国际化格式集中处理，不依赖浏览器隐式转换。
- 请求应支持取消或忽略过期响应，避免页面卸载后更新状态及请求竞态覆盖新结果。
- 缓存键、失效、刷新和乐观更新策略集中定义，不在页面中零散实现。

### 5.1 错误边界

- 网络、异步、JSON 解析等可能失败的操作必须进入明确的错误边界，但不要求每个调用点机械包一层 `try/catch`。
- 统一 request 层处理通用错误；只有当前组件能够恢复、补偿或补充上下文时才就地捕获。
- 捕获后必须选择错误提示、降级数据、重试入口、日志上报或继续抛出，禁止静默吞错。
- 页面级渲染异常使用 Error Boundary 或框架等价能力，避免整站白屏。
- 不得用假数据伪装请求成功；降级数据必须可识别且不会被当作真实业务数据提交。

## 6. SSE 与流式交互（如适用）

- `event`、`data`、结束、心跳、错误和重连语义必须与后端契约严格一致。
- SSE 解析、取消、重连和事件分发集中封装，不在不同页面复制解析器。
- token/增量内容按帧或批次更新，避免每个 token 触发一次 React 状态更新。
- 使用 `AbortController` 或等价机制处理页面离开、用户取消和请求替换。
- 代理必须关闭不适用的响应缓冲并放宽长连接超时；相关配置纳入环境验证。
- 断线重连必须有次数、退避、幂等和重复事件处理策略，不允许无限重连。
- 流式日志只记录摘要、耗时、事件数和错误，不打印完整敏感内容。

## 7. React 组件、Hooks 与状态

- 使用函数组件和 Hooks；Class 组件只用于既有兼容场景。
- 组件使用明确的 Props 类型，组件名、导出名和文件语义保持一致。
- Hooks 只在顶层调用；自定义 Hook 以 `use` 开头，副作用依赖必须完整。
- 订阅、定时器、请求和事件监听在 effect 清理函数中释放。
- 页面/组件优先使用局部状态；只有跨页面或跨模块共享且生命周期明确的数据进入全局状态。
- 不冗余保存可由 props、请求结果或其他状态推导的数据。
- 列表使用稳定业务 key，不使用可能变化的数组下标代替身份。
- `useMemo`、`useCallback` 和组件 memoization 只在有稳定性需求或性能证据时使用，不作为默认样板。
- 组件过大、职责混杂或难以测试时拆分；行数和圈复杂度作为评审信号，不以机械阈值代替职责判断。

## 8. 异步状态与用户体验

- 每个异步场景根据适用性处理初始、加载、成功、空数据、失败、重试、过期和取消状态。
- 长耗时操作提供明确反馈；提交操作防止重复触发，并说明成功、失败和必要的回滚行为。
- 加载状态避免页面大幅跳动；骨架屏、占位和最终内容的尺寸尽量一致。
- 登录失效、无权限、资源不存在、限流和服务异常应可区分，并提供可执行的恢复入口。
- 错误提示使用用户可理解的语言，不直接展示堆栈、内部错误或后端原始敏感消息。

## 9. 样式、设计系统与响应式

- 优先使用 Ant Design 组件和 Design Token；颜色、字号、间距、圆角、阴影、层级和断点不得散写魔法值。
- 样式默认使用 LESS/CSS Modules，避免全局污染；全局样式必须有明确适用范围。
- 优先使用 Flex/Grid；避免依赖脆弱 DOM 层级、标签选择器和 `!important`。
- 类名遵循项目工具链约定，语义描述职责而不是视觉偶然状态。
- 响应式断点使用预定义变量或 mixin，不在业务文件中散写媒体查询数值。
- `px`、`rem`、`vw/vh` 和百分比按语义使用；不机械禁止 `px`，也不混用未经统一换算的设计稿单位。
- 图标优先 SVG 或既有图标系统；图片提供正确尺寸、压缩、懒加载和必要的响应式资源。

## 10. 无障碍

- 项目目标默认不低于 WCAG 2.2 AA；无法满足项在工单记录原因和修复计划。
- 使用语义化 HTML，保证键盘可操作、焦点可见、焦点顺序合理。
- 可点击区域应满足设计系统或移动端至少约 44×44 CSS px 的目标。
- 表单控件必须有关联标签；错误信息可被辅助技术识别，并说明恢复方式。
- 图片提供合适替代文本；纯装饰图像不制造无意义朗读。
- 不把颜色作为传递状态的唯一方式；动效尊重 `prefers-reduced-motion`。
- 默认允许用户缩放；只有经过无障碍评估的封闭场景才可限制缩放。

## 11. H5 与移动端适配（如适用）

- 使用 `width=device-width, initial-scale=1, viewport-fit=cover`；缩放策略遵循无障碍要求。
- 设计稿基准、换算工具和断点全项目统一，不在页面内自行实现另一套适配方案。
- 安全区域使用 `env(safe-area-inset-*)`，不硬编码状态栏或 Home Indicator 高度。
- 输入框按场景设置 `type`、`inputMode` 和自动填充属性，提供合适软键盘。
- 使用 `visualViewport`、`scrollIntoView` 或项目验证过的方案处理软键盘遮挡；禁止无依据地全局滚动复位。
- 触摸交互采用现代浏览器支持的 `touch-action` 等能力，不重复引入过时点击延迟补丁。
- 禁止用全局 `overflow-x: hidden` 掩盖布局溢出；必须定位并修复真实溢出来源。
- 固定定位、滚动容器、横竖屏、刘海屏和低端机必须在目标真机或等价环境验证。
- 动画优先 `transform`/`opacity`，避免频繁布局与重绘；弱网场景提供超时和重试反馈。

## 12. 命名、常量与代码卫生

- 变量和函数使用小驼峰，组件/类型使用大驼峰，真正的模块级常量使用全大写下划线。
- 布尔命名优先使用 `is/has/can/should` 等可读前缀。
- 文件名统一使用小写中划线；若框架或既有仓库有不同约定，以项目基线为准。
- 具有业务语义的阈值、枚举、存储键、事件名、超时和 URL 前缀必须常量化。
- 不机械抽取 `0`、`1`、空数组等无歧义语言值；常量应增加语义，而不是搬运字面量。
- 同一概念的命名与正式规格、后端契约和埋点字典保持一致。
- 注释解释原因、约束和非显然取舍，不复述代码；过期注释和 TODO 必须清理。

## 13. 安全、配置与浏览器存储

- 路由参数、查询参数、接口数据、Markdown/HTML 和跨窗口消息均按不可信数据处理。
- 原始 HTML/Markdown 必须使用经过批准的净化方案，禁止自行拼接绕过。
- 前端权限只控制界面和交互，不能代替服务端鉴权。
- 禁止在代码、仓库、构建产物、Source Map、日志或埋点中写入密钥和内部敏感配置。
- Cookie、LocalStorage、SessionStorage 和 IndexedDB 不保存不必要的凭据或敏感业务数据；存储内容必须有生命周期和清理策略。
- 外部跳转、回调地址和下载链接必须校验，防止开放重定向和危险协议。
- 依赖新增前检查维护状态、许可证、安全漏洞、包体积和工具链兼容性。
- 安全策略、CSP、CSRF、Cookie 属性和 Source Map 发布方式按部署环境明确配置。

## 14. 埋点与前端可观测性

- 每个页面及关键交互根据埋点方案覆盖曝光、点击、提交和关键转化；埋点属于 `WEB-TASK` 交付物。
- 工单验收标准必须列出新增、修改和删除的点位；缺失必需埋点时工单不得完成。
- 事件命名、触发时机、去重规则、公共参数和业务参数全项目统一，新事件登记到埋点字典。
- 数据口径与产品/后端正式定义一致，不根据 DOM 偶然结构或展示文案推断业务字段。
- 修改页面交互时同步维护埋点，避免漏报、重复上报和指标污染。
- 埋点、错误监控和日志执行隐私最小化；长文本、凭据和敏感字段不采集或先脱敏。
- 关键用户旅程应能通过 trace/request ID、错误事件和版本信息定位失败阶段。

## 15. 性能

- 工单对有风险的性能路径给出可验证目标；项目基线填写 Core Web Vitals、首屏资源和包体预算。
- 页面和路由按收益进行代码分割；大型依赖引入前评估实际使用范围与替代方案。
- 图片懒加载、压缩并保留尺寸占位，降低网络开销和 CLS。
- 大列表在数据规模达到阈值时采用分页、窗口化或虚拟列表。
- 资源按场景使用 preload/prefetch，不无差别预加载。
- gzip/brotli、缓存 Header、CDN 和静态资源版本由构建/部署基线统一配置。
- 使用性能分析工具定位无效渲染，再决定 memoization；禁止没有证据的“性能优化”增加复杂度。

## 16. 测试与质量门禁

每个 `WEB-TASK` 至少验证业务验收标准，并按风险选择：

- 纯函数、格式化、契约转换和复杂状态：单元测试。
- 组件交互、表单校验、错误边界和异步状态：组件/集成测试。
- 跨页面关键旅程、路由、权限和真实接口协作：端到端测试。
- 契约、SSE 事件和兼容性：契约/集成测试。
- 视觉、响应式、键盘操作、无障碍和浏览器兼容：自动化检查配合必要人工验证。

测试规则：

- 查询元素优先使用角色、标签和稳定测试标识，不依赖脆弱 CSS 层级或展示顺序。
- 不使用固定延时掩盖异步竞态；等待可观察状态或事件。
- mock 数据必须符合正式契约并集中维护，不能掩盖真实集成问题。
- flaky test 不得仅靠重试长期掩盖，必须记录负责人并限期修复。
- Light/Standard `WEB-TASK` 只运行对应页面、API 契约和直接依赖的定向测试；完整浏览器套件在整轮合入后由最终 Heavy Task 统一运行一次。
- 连接真实后端的页面验证复用工程长期验证数据库，不为每个页面 Task 反复创建、删除数据库容器。

合并或交付前至少通过：

| 门禁 | 项目命令/工具 | 是否必须 |
|---|---|---|
| 依赖安装一致性 | 待填写 | 是 |
| 格式化与 lint | 待填写 | 是 |
| TypeScript 类型检查 | 待填写 | 是 |
| 单元/组件测试 | 待填写 | 是 |
| 端到端/契约测试 | 待填写 | 按改动 |
| 生产构建 | 待填写 | 是 |
| 依赖与敏感信息扫描 | 待填写 | 是 |
| 浏览器/视口/无障碍检查 | 待填写 | 按工单 |
| 性能与包体预算 | 待填写 | 按风险 |

具体命令和实际结果写回工单，不得记录未执行的检查。

## 17. 改动边界与工具链纪律

- 实现范围必须与 `WEB-TASK` 一致，顺手重构、改名、批量格式化和依赖升级另建工单。
- 纯样式需求默认只修改相关样式；若必须调整结构或逻辑，先在工单/评审中说明原因和影响。
- 沿用仓库现有构建工具、模块制式和配置写法，不擅自迁移 webpack/vite/Umi、ESM/CJS 或文件扩展名。
- 新增依赖优先选择与当前工具链兼容的版本；构建链迁移必须单独建立 ADR/Task。
- 既有代码存在问题但不影响当前交付时，记录后续任务，不夹带无验证的静默重构。

## 18. 发布、兼容与回滚

- 发布前检查后端契约、环境配置、权限、埋点、监控、浏览器兼容和性能预算。
- Feature Flag 必须有负责人、默认值、环境策略、观测方式和清理日期。
- 灰度发布定义成功指标和停止条件；异常时能快速关闭入口或回滚静态资源版本。
- Source Map 按安全策略上传到受控监控系统，不公开泄露源码和内部路径。
- 发布后在观察窗口确认前端错误率、接口失败率、关键转化、性能和用户反馈。
