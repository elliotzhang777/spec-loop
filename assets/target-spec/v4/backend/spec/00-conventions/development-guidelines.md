## 1. 规范强度与例外

- **必须/禁止**：不可绕过；无法满足时必须建立 ADR，并在 Design 中给出风险、补偿和恢复计划。
- **应该**：默认遵守；例外需在 Design 或 Task 中记录原因。
- **可以**：按场景选择，不作为验收门禁。
- 新增核心框架、基础设施、跨模块依赖或难以回退的技术选择，必须在 [`03-decisions/`](../03-decisions/) 建立 ADR。
- 本文件不列具体业务表、字段和领域模型，避免形成第二事实源。

### 2.1 Maven 模块职责

默认采用 5 个 Maven 子模块；若项目结构不同，初始化时替换本表并在 Architecture 中记录依赖方向。

| 模块 | 职责 | 允许放置 | 禁止放置 |
|---|---|---|---|
| `common` | 无业务、无 IO 的公共基础 | 枚举、异常、DTO/Request、响应包络、用户上下文、工具和开关 | 数据访问、远程调用、业务流程 |
| `dal` | 数据与外部依赖防腐层 | Domain/Mapper、Repository、缓存/搜索、外部 RPC/HSF 消费、消息和 HTTP 适配 | 业务编排、对外 Web 接口 |
| `service` | 业务规则与用例实现 | 领域服务、应用服务、内部接口 | SQL、远程 SDK/协议类型、Controller |
| `client` | 本服务提供给其他应用的对外契约 | 接口、请求/响应 VO | 内部实现、本服务消费外部系统的客户端 |
| `start` | 启动与协议接入 | Controller、启动类、配置、AOP、全局异常处理 | 持久化细节、核心业务规则 |

默认依赖方向为 `start → service → dal → common`；`client` 作为独立对外契约，由 `service/start` 实现但不反向依赖业务实现。禁止反向、成环和跳层；Controller 不直接调用 dal，service 不直接写 SQL 或调用外部协议。

## 3. 模块边界与依赖方向

- 依赖方向必须符合 [`architecture.md`](../architecture.md)，禁止反向依赖、循环依赖和无记录的跨层调用。
- Controller/RPC Handler 只负责协议转换、校验和调用编排，不直接访问数据库或外部系统。
- 业务层只依赖内部接口和内部模型，不直接依赖 SQL、远程 SDK、消息客户端或外部协议类型。
- 业务规则不得散落在 Controller、Mapper/XML、序列化配置或数据库触发器中。
- 模块对外暴露最小 API；禁止跨模块引用实现包或绕过公开接口。
- 共享代码只有在语义稳定并被多个模块复用时才上提，不建立“万能 common”。

## 4. 外部依赖与防腐层

- 数据库、缓存、搜索、对象存储、RPC/HSF、HTTP、消息和第三方 SDK 一律通过 `dal` 防腐层接入。
- 适配层负责把外部请求、响应、错误和状态转换为内部模型与稳定异常；业务层不得识别第三方 SDK 类型。
- 外部调用必须明确超时、重试、退避、熔断、限流和幂等策略；禁止无界重试。
- 重试只用于可安全重试的操作，并纳入总超时预算；不得让多层重试产生放大效应。
- 依赖不可用时默认明确失败或降级，禁止用 mock、随机结果或假数据伪装成功并污染下游。
- 外部协议升级、SDK 替换或兼容逻辑集中在适配层，不扩散到业务代码。

## 5. 对外契约与 API 演进

- “对外契约模块”只保存本服务提供给调用方的接口和模型，不存放本服务消费外部系统的客户端实现。
- REST、RPC、消息和流式事件的字段、可空性、枚举、错误码及兼容策略必须在正式契约中定义。
- REST 默认使用 `/api/v1` 版本前缀；若采用其他策略，在项目基线中明确。响应默认使用统一 `ApiResult<T>` 包络，并统一分页、错误格式和追踪标识。
- 对外请求/响应模型与内部领域模型分离，不直接暴露数据库实体、内部审批字段或敏感字段。
- 破坏性变更必须新建版本或提供兼容期、迁移说明、调用方清单和下线计划。
- 修改 REST、RPC、消息或流式事件时，必须同步相关调用方规格和契约测试。
- 接口弃用必须可观测，并在确认无调用后按计划删除，不无限期保留双实现。

## 6. 数据访问、DDL 与生成代码

- 数据结构变更必须按“模型/Design → 更新 DDL 与数据字典 → 开发评审 → 受控平台执行迁移 → 运行代码生成器 → 验证”流转。
- DDL、数据字典、迁移脚本和生成物必须在同一交付中保持一致。
- ORM/Mapper 等生成目录必须明确标识，生成物禁止手改；字段变更回到 DDL/模型后重新生成。使用 MyBatis Generator 时，`domain/`、基础 Mapper 和 XML 均视为生成物。
- 扩展查询放在 `mapper/ext/` 或项目约定的独立扩展目录，避免生成器覆盖；持久层只负责存取，不承载业务规则。
- 默认数据库基线为 MySQL、InnoDB、utf8mb4；每张表和每个字段必须有 `COMMENT`。
- 新表默认包含 `id`、`gmt_create`、`gmt_modified` 和 `is_deleted`。字段类型、自动更新时间和主键策略在项目基线中统一，例外必须在 Design 中说明。
- 跨系统对齐使用稳定业务编码，不依赖仅在单库内有意义的自增主键。
- 业务唯一性优先由数据库唯一约束保证；暂时只能应用层去重时，必须记录竞态风险和补约束计划。
- 查询必须关注索引、分页稳定性、批量访问和 N+1 问题；性能敏感查询在 Design 中给出验证证据。

## 7. 软删除、枚举与状态

- 新表默认使用 `is_deleted` 软删标记；若项目统一选择 `deleted_at`，必须在项目初始化时替换，不混用两套语义。
- 软删数据默认不出现在正常查询中；恢复、唯一约束、归档和物理清理策略必须明确。
- 布尔值在数据库、内部模型和对外契约之间显式转换，并明确 NULL 语义。
- 状态和类型字段必须使用枚举或值对象，写入时校验合法取值；禁止裸解析外部值后直接入库。
- 状态迁移必须校验来源状态和目标状态，复杂状态机在 Design 中定义。

## 8. 入参校验与异常

- 所有外部输入均不可信，包括 HTTP/RPC 参数、消息、文件、Header 和 Agent/LLM 工具入参。
- 参数类型、长度、格式、范围、枚举和交叉字段约束在协议边界校验；非法输入返回稳定的客户端错误，不转成系统异常。
- 数字、金额、日期等使用统一解析工具，明确“必填、空值、默认值、非法值”四种行为。
- 业务异常默认使用 `BizException(ErrorCode, message)` 或项目基线中的等价类型；全局异常处理器负责转换为 `ApiResult<T>` 与日志映射。
- 对外错误需说明调用方可采取的下一步，不暴露 SQL、堆栈、内部地址、密钥或实现细节。
- 未知异常统一兜底并保留 trace/correlation ID，便于服务端定位。

## 9. 事务、幂等与跨存储一致性

- 多步单库写入必须有明确事务边界；事务内避免长耗时远程调用和无上限批处理。
- 不得假设本地事务可以回滚缓存、搜索、对象存储、消息或远程系统。
- 跨存储写入必须在 Design 中明确事实源、执行顺序、幂等键、补偿、重试和对账策略；按场景选择 Outbox、Saga 或等价机制。
- 外部来源数据使用稳定的外部 ID 或业务唯一键幂等，重导默认覆盖/更新，不重复堆积。
- 可重算资源使用稳定可复算 ID；除非身份本身要求随机性，不用随机 UUID 破坏重跑幂等。
- 删除跨存储数据时必须防止孤儿和悬空引用；失败进入可重试的待清理集合并告警。
- 涉及外部存储或外部数据源时，应提供 reconcile 能力识别、报告并修复不一致。
- 写接口明确重复请求、超时后重试和并发提交的行为。

## 10. 并发、异步与资源管理

- 默认按多实例部署设计，不以“当前只有一个实例”作为正确性前提。
- 定时任务、抢占和状态更新使用数据库 CAS、分布式锁或等价机制，并明确锁超时与故障恢复。
- 高频累加、热点资源和批处理必须评估锁粒度、竞争、背压和资源上限。
- `ThreadLocal`、连接、流、临时文件和线程池资源必须在 `finally` 或等价机制中释放。
- 异步任务使用请求期资源前，必须在请求结束前复制必要数据与可信上下文，不持有已失效的请求对象。
- 异步传播用户、租户、trace 等上下文时采用显式快照，不依赖线程复用的隐式状态。
- 线程池、队列、批大小和超时必须有界，并有拒绝、降级和观测策略。

## 11. 流式与长连接接口（如适用）

- SSE/WebSocket/流式 RPC 的事件名、顺序、结束、心跳、重连和错误语义必须形成正式契约。
- 流式事件新增或变更必须同步调用方解析逻辑和契约测试。
- 代理缓冲、连接超时、异步超时和最大并发按长连接场景显式配置。
- 读取流、回调线程和上下文传播必须符合运行容器约束，避免把工作丢到不受控线程。
- 客户端断开后应尽快取消下游工作并释放资源；慢消费者需要背压或限流策略。
- 日志不得逐片打印完整内容；按请求记录摘要、耗时、事件数和错误。

## 12. Agent/MCP/工具接口（如适用）

- Agent 工具属于机器接口，不等同普通前端接口；新增或修改前必须建立 Design，说明用途、入参、返回、权限和测试方式。
- 工具名保持稳定、动作明确且单一职责；描述需说明何时调用、返回什么以及禁止用途。
- 入参只保留用户会稳定表达的字段；返回最小必要信息，不暴露内部 DTO、密文、审批字段或无关噪声。
- 调用来源鉴权与最终用户授权必须分开：服务凭证只证明调用方可信，不代表用户具有数据权限。
- 用户、租户、部门和权限范围只从网关、登录态或受信运行时上下文取得，不信任模型生成的身份字段。
- 写工具默认不开放；确需开放时必须建立 ADR/Design，补齐确认或审批、审计、幂等、防误操作、回滚和灰度。
- 错误需区分鉴权失败、参数错误、权限不足、业务错误和系统异常，并给出可执行的恢复提示。
- 记录结构化调用日志，包括工具、调用来源、可信用户、trace/会话标识、耗时、结果和错误码；长文本截断，敏感内容脱敏。
- 发布前至少验证：缺失/错误凭证、缺失身份、越权、正常调用、歧义输入、重复写入和 trace 串联。

## 13. 配置、依赖与运行时隔离

- 配置按环境分层，必需配置在启动时校验；禁止以危险默认值带病启动。
- 密钥、Token 和证书由密钥/配置系统托管，不写入代码、仓库、镜像或普通日志。
- 空凭证配置必须拒绝受保护调用，不得退化为匿名开放。
- 本地调试、绕过鉴权和 mock 开关必须默认关闭，并阻止进入生产环境。
- 新增依赖前检查维护状态、许可证、安全漏洞、版本兼容和运行成本；依赖版本必须锁定。
- CI 应执行依赖漏洞与凭证泄漏扫描，并定义升级与处置时限。
- 插件、容器或沙箱存在类加载隔离时，反射对象和类型必须由正确的 ClassLoader 创建和加载。
- 不假设本地依赖版本与运行容器一致；使用受支持 API，并在目标运行环境做集成验证。

## 14. 安全与敏感信息

- 身份认证和数据授权在可信服务端边界执行；不信任前端传入的工号、创建人、租户或权限范围。
- 多租户查询、缓存键、消息和后台任务必须携带并校验租户边界。
- 管理和高风险接口需要更严格的授权、审批、审计和限流。
- 出站 URL 必须校验协议、域名、解析地址和重定向，防止 SSRF 访问内网、localhost 或元数据服务。
- 数据库、模板、命令和日志输出按场景防止注入；默认不执行或渲染不可信内容。
- 敏感字段按分类加密或脱敏；API、日志、指标、追踪、事件和错误响应均执行最小披露。
- 安全相关失败默认拒绝，不使用“失败则放行”的降级策略。

## 15. 日志与可观测性

- 生产默认使用合适的 INFO 级别；高频路径避免逐条刷屏，DEBUG 仅按需开启。
- 使用结构化日志，至少包含 trace ID、关键业务标识、动作、结果、耗时和稳定错误码。
- 长文本、集合和二进制内容在记录前截断或摘要；凭证、密文及不必要的个人信息禁止打印。
- 关键链路提供 RED/USE 或等价指标、分布式追踪、告警阈值和排障入口。
- 健康检查区分存活与就绪；服务支持优雅停机，停止接流后释放连接并完成或转移在途任务。
- 可观测性代码不得改变业务结果；采集失败不应阻塞核心链路，安全审计除外。

## 16. 测试与质量门禁

- 业务规则、边界条件、状态迁移和失败路径使用单元测试覆盖。
- 数据库、缓存、消息、外部适配和序列化契约使用集成或契约测试覆盖。
- 跨组件关键链路按风险增加端到端、迁移、并发、性能、安全或故障演练。
- 时间、随机数、外部 ID 和执行器应可控制，测试不得依赖顺序、真实时间或共享脏数据。
- 不得用 mock 通过代替对关键契约、迁移和真实集成边界的验证。
- flaky test 不得简单重试掩盖；必须隔离、记录负责人并限期修复。
- 测试覆盖率作为风险信号，不以单一百分比替代关键行为验证。
- Light/Standard Task 只运行自身 AC、改动模块和直接依赖的定向测试；整轮全量回归在所有 Task 合入后由最终 Heavy Task 统一运行一次。
- 工程应维护一个长期验证数据库，普通测试通过事务回滚、固定 Fixture 或受控 schema reset 恢复；不得为每个 Task 反复创建和删除数据库容器或数据卷。
- 从零迁移、初始化、升级/回滚或强隔离测试可以使用一次性数据库，但必须属于 Heavy 验证并在工单中记录原因。

合并或交付前至少通过项目配置的：

| 门禁 | 项目命令/工具 | 是否必须 |
|---|---|---|
| 依赖安装与构建一致性 | 待填写 | 是 |
| 格式化 | 待填写 | 是 |
| 静态检查/编译 | 待填写 | 是 |
| 单元与集成测试 | 待填写 | 是 |
| 数据迁移/契约检查 | 待填写 | 按改动 |
| 安全与依赖扫描 | 待填写 | 是 |
| 生产构建/制品验证 | 待填写 | 是 |
| 性能或故障验证 | 待填写 | 按风险 |

不得记录未实际执行的检查；命令、结果和必要证据写回 Task。

## 17. 发布、兼容与回滚

- 发布前检查调用方兼容、数据迁移顺序、配置完整性、容量、安全和可观测性。
- 数据库变更优先采用 expand-contract：先兼容扩展，再迁移流量/数据，最后删除旧结构。
- Feature Flag 必须有负责人、默认值、环境策略、观测方式和清理日期；禁止永久保留废弃分支。
- 灰度发布定义成功指标和自动/人工停止条件；异常时优先阻止扩大影响。
- 回滚方案必须覆盖代码、配置、数据和外部契约；不可逆变更需在发布前明确前滚修复方案。
- 发布后在约定观察窗口确认错误率、延迟、资源、关键业务指标和日志告警。

## 18. 命名、注释与代码卫生

- 命名使用领域语言并与正式规格一致；同一概念禁止在不同层使用多套名称。
- 对外接口、事件和工具名保持稳定、动作明确；缩写和命名风格按项目基线统一。
- 注释说明原因、约束和非显然取舍，不复述代码；过期注释与 TODO 必须清理。
- 删除废弃代码、调试输出和无效配置，不保留平行实现或注释掉的大段代码。
- 生成代码、第三方代码和人工代码边界清晰，评审时不混入无关格式化噪音。
