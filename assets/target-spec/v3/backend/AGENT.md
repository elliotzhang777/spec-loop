# 后端服务规格驱动交付约定

本工程采用规格驱动开发。AI 和人工协作者必须以 `spec/05-task/` 中的工单为最小执行单位，并以工单验收标准作为完成依据。

## 开始工作前

1. 阅读 `spec/roadmap.md`，确认目标与优先级。
2. 阅读 `spec/architecture.md`，确认项目级技术边界和约束。
3. 阅读 `spec/00-conventions/development-guidelines.md` 和工单引用的 Decision。
4. 阅读工单引用的 Product、Feature 和 Design。
5. 检查 `spec/pending-board.md` 和 `spec/verification-board.md`。
6. 若需求尚未形成可执行工单，先补齐上游规格并创建工单，不直接实现模糊需求。

## 规格层级

`Roadmap -> Product -> Feature -> Design -> Task -> 实现与验证`

`Architecture -> Design -> Task -> 实现与验证`

`Decision -> Architecture / Design / Task`

- Roadmap：项目阶段、目标和产品方向。
- Product：用户、问题、范围和成功指标。
- Feature：单项能力、行为规则和业务验收标准。
- Architecture：系统边界、组件职责、数据与部署架构及横切技术约束。
- Design：技术方案、接口、数据、风险和验证策略。
- Task：可独立实现、验证和关闭的后端工单。
- Convention：所有后端任务共同遵循的长期开发规范。
- Decision：跨特性、影响长期技术方向且需要保留背景与取舍的架构决策。

下游文档必须引用上游文档 ID；Design 还必须引用总体技术架构。需求或架构变化应从受影响的最高层开始更新，并同步所有下游文档。

## 工单执行规则

- 后端工单使用 `TASK-###`。
- 一次只执行一个明确工单；超出范围的工作另建工单。
- Task/Loop 启动和“继续执行”只授权实现与快速反馈检查；未获得当前稳定候选的显式正式验证授权，不得运行完整 Harness、独立 Verifier 或全量回归。
- 用户拒绝结果或候选继续变化后，旧的正式验证授权立即失效；阶段验收与进入下一阶段还需独立确认。
- 非 Heavy 工单只运行自身 AC、改动模块和直接依赖的定向 Gate，不得运行全量回归；整轮功能合入后由最终 Heavy 工单统一验证一次。
- 已配置长期验证数据库时必须复用，普通工单不得反复创建、删除数据库容器或数据卷；优先使用事务回滚、固定 Fixture 或受控 schema reset。
- 一次性干净数据库仅用于迁移、初始化、升级/回滚或明确隔离场景，并由 Heavy 工单记录使用原因。
- 开始时把工单状态改为 `进行中`，并更新 `spec/pending-board.md`。
- 实现必须覆盖全部验收标准；不得用“代码已写”代替“验收通过”。
- 完成实现后，在工单“交付记录”中填写变更文件、关键决策、测试结果和遗留风险。
- 需要人工或独立验证时，将工单加入 `spec/verification-board.md` 并把状态改为 `待验证`。
- 验证通过后，把证据和结论写回工单，状态改为 `已完成`，并同步相关 Design、Feature 和 Product。
- 最后从两个看板删除已关闭条目。看板不保存历史，工单和上游规格保存完整历史。

## 完成定义

只有同时满足以下条件，工单才算完成：

- 验收标准逐项通过；
- 相关测试或检查已运行并记录结果；
- 实际交付与原设计的差异已记录；
- 上游规格的状态和实际结果已同步；
- 验证结论已写回正式规格；
- 两个看板中不再保留该工单条目。

## 文档规则

- ID 格式：`PROD-###`、`FEAT-###`、`DES-###`、`TASK-###`。
- 架构决策 ID：`ADR-###`，文件保存在 `spec/03-decisions/`。
- 文件名格式：`<ID>-<kebab-case-name>.md`，模板文件除外。
- 链接使用相对路径；同一概念只保留一个权威定义。
- 状态仅使用：`草稿`、`已批准`、`进行中`、`待验证`、`已完成`、`已取消`。
- 禁止删除已经完成的工单；如需纠正，追加变更记录或建立后续工单。
